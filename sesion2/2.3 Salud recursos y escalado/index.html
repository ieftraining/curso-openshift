    2.3 Salud, recursos y escalado

    Objetivos

    Al finalizar este apartado serás capaz de:

    • Comprender cómo OpenShift supervisa el estado de una aplicación.
    • Diferenciar startupProbe, readinessProbe y livenessProbe.
    • Entender por qué readiness y liveness tienen objetivos distintos.
    • Configurar comprobaciones de salud mediante sondas HTTP.
    • Definir requests y limits básicos.
    • Comprender el funcionamiento general del autoescalado horizontal (HPA).

    Actualización a la versión v3

    Hasta este momento estamos trabajando con la versión v2 de la aplicación, utilizada anteriormente para demostrar actualizaciones de imagen, rollouts y rollbacks.

    Para poder explicar las sondas de salud vamos a desplegar una nueva versión.

    La versión v3 incorpora varios endpoints específicamente diseñados para este propósito:

    /version
/live
/ready

    Registrando la causa del cambio y actualizando la imagen

    Para asegurar que la causa del cambio quede correctamente registrada en el historial de revisiones del Deployment, modificamos el archivo deployment.yaml actualizando la imagen a v3 e incluyendo la anotación kubernetes.io/change-cause en la sección metadata.

    Opción 1: mediante YAML (Recomendado)

    Modificar el manifiesto deployment.yaml completo:

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-formacion-yaml
  annotations:
    kubernetes.io/change-cause: "Actualizacion a v3. Incorpora endpoints /version, /live y /ready para demostracion de probes."

spec:
  replicas: 1

  selector:
    matchLabels:
      app: demo-formacion-yaml

  template:
    metadata:
      labels:
        app: demo-formacion-yaml

    spec:
      containers:
      - name: demo-formacion
        image: docker.io/ieftraining/demo-formacion:v3
        imagePullPolicy: Always

        ports:
        - containerPort: 8080

    Y aplicar los cambios:

    oc apply -f deployment.yaml

    Opción 2: desde línea de comandos

    oc set image deployment/demo-formacion-yaml \
  demo-formacion=docker.io/ieftraining/demo-formacion:v3

oc annotate deployment/demo-formacion-yaml \
  kubernetes.io/change-cause="Actualizacion a v3. Incorpora endpoints /version, /live y /ready para demostracion de probes." \
  --overwrite

    Opción 3: desde la consola web

    • Abrir el Deployment.
    • Seleccionar Actions → Edit Deployment.
    • Modificar la imagen del contenedor a docker.io/ieftraining/demo-formacion:v3.
    • Actualizar la anotación kubernetes.io/change-cause dentro del bloque metadata.annotations.
    • Guardar los cambios.

    OpenShift iniciará automáticamente un nuevo rollout.

    Comprobando el despliegue

    oc rollout status deployment/demo-formacion-yaml

    o bien:

    oc get pods -w

    Consultando el histórico

    oc rollout history deployment/demo-formacion-yaml

    Ejemplo de resultado esperado:

    REVISION  CHANGE-CAUSE
1         Creacion inicial de la aplicacion v1.
2         Actualizacion a v2. Nueva version de la aplicacion para demostracion de actualizaciones y rollback.
3         Actualizacion a v3. Incorpora endpoints /version, /live y /ready para demostracion de probes.

    Detalle de una revisión específica:

    oc rollout history deployment/demo-formacion-yaml --revision=3

    Verificando la nueva versión

    Abrimos la URL de nuestra Route publicada en el navegador:

    [https://demo-formacion-yaml.apps](https://demo-formacion-yaml.apps).../version

    Resultado esperado:

    {
  "version": "v3"
}

    A partir de este momento podemos comenzar a estudiar cómo OpenShift supervisa la aplicación utilizando los endpoints /live y /ready.

    Supervisión de aplicaciones en OpenShift

    En el apartado anterior hemos desplegado nuestra aplicación mediante un Deployment y la hemos publicado utilizando un Service y una Route.

    La aplicación es accesible desde el navegador:

    [https://demo-formacion-yaml.apps](https://demo-formacion-yaml.apps)...

    Sin embargo, OpenShift necesita responder continuamente a preguntas como:

    • ¿La aplicación sigue funcionando?
    • ¿Ha terminado de arrancar?
    • ¿Está preparada para recibir tráfico?
    • ¿Debo reiniciarla?
    • ¿Debo dejar temporalmente de enviarle peticiones?

    Para responder a estas preguntas Kubernetes utiliza las denominadas probes o sondas de salud.

    La versión v3 de nuestra aplicación

    La versión v3 incorpora varios endpoints específicos:

    /version
/live
/ready

    Probando los endpoints

    Podemos probar individualmente las rutas desde el navegador o mediante curl:

    [https://demo-formacion-yaml.apps](https://demo-formacion-yaml.apps).../version
[https://demo-formacion-yaml.apps](https://demo-formacion-yaml.apps).../live
[https://demo-formacion-yaml.apps](https://demo-formacion-yaml.apps).../ready

    La propia aplicación nos servirá para entender qué está comprobando OpenShift en cada momento.

    Simulación de un arranque lento

    Para facilitar la explicación de las probes hemos modificado la aplicación en su versión v3.

    Cuando el contenedor arranca:

    /live  -> OK (200)
/ready -> NOT READY (500)

    durante aproximadamente 30 segundos.

    Pasado ese tiempo:

    /live  -> OK (200)
/ready -> READY (200)

    ¿Por qué hemos hecho esto?

    Muchas aplicaciones necesitan un tiempo adicional para completar su inicialización.

    Por ejemplo:

    • Cargar configuración.
    • Inicializar componentes internos.
    • Construir cachés.
    • Ejecutar migraciones.
    • Conectar con servicios externos.
    • Cargar información en memoria.

    Por tanto: una aplicación puede estar funcionando y, sin embargo, no estar todavía preparada para recibir peticiones.

    Esta diferencia es precisamente la que intentan resolver readiness y liveness.

    Readiness Probe

    La readiness probe responde a una única pregunta:

    ¿Puede este Pod recibir tráfico ahora mismo?

    • Si la respuesta es afirmativa: El Service enviará tráfico al Pod.
    • Si la respuesta es negativa: El Pod continúa ejecutándose, pero se retira temporalmente de los endpoints del Service para dejar de recibir tráfico.

    Añadiendo una Readiness Probe

    Partimos de nuestro Deployment v3 y le incorporamos la configuración de la probe.

    Manifiesto deployment.yaml completo:

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-formacion-yaml
  annotations:
    kubernetes.io/change-cause: "Anadida readinessProbe en endpoint /ready"
spec:
  replicas: 1
  selector:
    matchLabels:
      app: demo-formacion-yaml
  template:
    metadata:
      labels:
        app: demo-formacion-yaml
    spec:
      containers:
        - name: demo-formacion
          image: docker.io/ieftraining/demo-formacion:v3
          imagePullPolicy: Always
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            periodSeconds: 5

    ¿Qué acabamos de añadir?

    Únicamente el bloque:

    readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  periodSeconds: 5

    A partir de este momento OpenShift realizará peticiones periódicas cada 5 segundos contra /ready para decidir si el Pod puede o no recibir tráfico.

    Aplicación de los cambios

    Opción 1: mediante YAML (Recomendado)

    Si disponemos del manifiesto actualizado:

    oc apply -f deployment.yaml

    Opción 2: desde línea de comandos

    oc set probe deployment/demo-formacion-yaml \
  --readiness \
  --get-url=http://:8080/ready \
  --period-seconds=5

    Opción 3: desde la consola web

    • Abrir el Deployment demo-formacion-yaml.
    • Seleccionar Actions → Edit Deployment.
    • Añadir el bloque readinessProbe dentro del contenedor.
    • Guardar los cambios.

    OpenShift generará automáticamente una nueva revisión del Deployment sin necesidad de detener ni eliminar el recurso previamente.

    Observando el comportamiento

    Podemos monitorizar el estado del Pod mediante:

    oc get pods -w

    Al arrancar una nueva revisión veremos algo parecido a:

    NAME                                   READY   STATUS    RESTARTS   AGE
demo-formacion-yaml-6d4b65b98b-x8z2p   0/1     Running   0          5s

    Esto significa: El contenedor está ejecutándose (Running), pero la columna READY indica 0/1 (la aplicación todavía no está preparada).

    Recordemos que /live responde OK pero /ready responde NOT READY durante los primeros 30 segundos.

    Pasados esos 30 segundos, la probe obtiene una respuesta correcta y observaremos:

    NAME                                   READY   STATUS    RESTARTS   AGE
demo-formacion-yaml-6d4b65b98b-x8z2p   1/1     Running   0          35s

    1/1 indica que OpenShift ya considera que el Pod está listo y el Service empieza a enviarle tráfico.

    Idea clave

    Durante esos primeros 30 segundos, la aplicación ya estaba funcionando en memoria. Lo único que ocurría es que OpenShift no la consideraba preparada. Ésa es exactamente la misión de la readiness probe.

    ¿Qué debe comprobar una Readiness Probe?

    Todo aquello que determine si la aplicación puede atender peticiones correctamente.

    Por ejemplo:

    • Configuración cargada.
    • Dependencias inicializadas.
    • Cachés preparadas.
    • Base de datos accesible.
    • Servicios críticos disponibles.

    La idea es: La aplicación sigue viva, pero todavía no está lista para prestar servicio.

    Liveness Probe

    La liveness probe responde a otra pregunta:

    ¿La aplicación sigue funcionando correctamente o se ha quedado bloqueada?

    Añadiendo una Liveness Probe

    Añadimos la comprobación de supervivencia sobre el endpoint /live.

    Manifiesto deployment.yaml completo:

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-formacion-yaml
  annotations:
    kubernetes.io/change-cause: "Configuradas readinessProbe y livenessProbe"
spec:
  replicas: 1
  selector:
    matchLabels:
      app: demo-formacion-yaml
  template:
    metadata:
      labels:
        app: demo-formacion-yaml
    spec:
      containers:
        - name: demo-formacion
          image: docker.io/ieftraining/demo-formacion:v3
          imagePullPolicy: Always
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /live
              port: 8080
            periodSeconds: 10

    ¿Qué hace?

    OpenShift ejecuta periódicamente GET /live cada 10 segundos.

    • Si recibe una respuesta HTTP correcta (200 OK), no realiza ninguna acción.
    • Si la comprobación falla repetidamente (error 500 o timeout), Kubernetes reiniciará automáticamente el contenedor.

    Aplicación de los cambios

    Opción 1: mediante YAML (Recomendado)

    Guardar el archivo deployment.yaml con la nueva sonda y aplicar:

    oc apply -f deployment.yaml

    Opción 2: desde línea de comandos

    oc set probe deployment/demo-formacion-yaml \
  --liveness \
  --get-url=http://:8080/live \
  --period-seconds=10

    Opción 3: desde la consola web

    • Abrir el Deployment demo-formacion-yaml.
    • Seleccionar Actions → Edit Deployment.
    • Añadir el bloque livenessProbe debajo de readinessProbe.
    • Guardar los cambios.

    ¿Qué debe comprobar una Liveness Probe?

    Únicamente aquello que permita saber que el proceso de la aplicación no se ha bloqueado.

    Por ejemplo:

    • El proceso principal sigue respondiendo.
    • El servidor web o la API responde a peticiones básicas.
    • No hay un bloqueo interno (deadlock).

    Readiness y Liveness no son intercambiables

    Readiness

    • Pregunta: ¿Puedo recibir tráfico?
    • Consecuencia de fallo: El Pod entra o sale de la lista de endpoints del Service.

    Liveness

    • Pregunta: ¿Sigo funcionando?
    • Consecuencia de fallo: Reinicio del contenedor por parte de Kubernetes.

    Ejemplo práctico

    Supongamos que una base de datos externa deja de responder temporalmente:

    /live  -> OK
/ready -> ERROR
    • Resultado correcto con Readiness: El Pod deja de recibir tráfico de los usuarios mientras la BD esté caída, pero el contenedor no se reinicia. Cuando la BD vuelve, /ready da OK y el tráfico se restaura solo.
    • Resultado incorrecto si usáramos solo Liveness: Si evaluáramos la BD en /live, Kubernetes reiniciaría el Pod una y otra vez en un bucle continuo (CrashLoopBackOff) sin resolver realmente el problema externo.

    Startup Probe

    Algunas aplicaciones empresariales (por ejemplo, Java/WildFly/Spring Boot) necesitan mucho tiempo para iniciar.

    Para evitar que la livenessProbe mate la aplicación antes de que termine de arrancar, se utiliza startupProbe.

    Añadiendo Startup Probe

    Manifiesto deployment.yaml completo con las tres sondas:

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-formacion-yaml
  annotations:
    kubernetes.io/change-cause: "Configuradas startupProbe, readinessProbe y livenessProbe"
spec:
  replicas: 1
  selector:
    matchLabels:
      app: demo-formacion-yaml
  template:
    metadata:
      labels:
        app: demo-formacion-yaml
    spec:
      containers:
        - name: demo-formacion
          image: docker.io/ieftraining/demo-formacion:v3
          imagePullPolicy: Always
          ports:
            - containerPort: 8080
          startupProbe:
            httpGet:
              path: /live
              port: 8080
            failureThreshold: 30
            periodSeconds: 1
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /live
              port: 8080
            periodSeconds: 10

    ¿Qué hace?

    Mientras la startupProbe no finalice correctamente (permite hasta 30 intentos × 1 segundo = 30 segundos de margen):

    • Readiness permanece inactiva.
    • Liveness permanece inactiva.

    Una vez que la startupProbe tiene éxito, se desactiva y da paso a la ejecución habitual de readiness y liveness.

    Aplicación de los cambios

    Opción 1: mediante YAML (Recomendado)

    oc apply -f deployment.yaml

    Opción 2: desde línea de comandos

    oc set probe deployment/demo-formacion-yaml \
  --startup \
  --get-url=http://:8080/live \
  --failure-threshold=30 \
  --period-seconds=1

    Opción 3: desde la consola web

    • Abrir el Deployment demo-formacion-yaml.
    • Seleccionar Actions → Edit Deployment.
    • Añadir el bloque startupProbe antes de readinessProbe.
    • Guardar los cambios.

    Buenas prácticas para las probes

    • Utilizar endpoints dedicados e independientes (ej. /live, /ready).
    • Evitar hacer comprobaciones pesadas o consultar la raíz /.
    • Mantener las comprobaciones simples y rápidas.
    • Separar claramente responsabilidades:
    • /ready -> disponibilidad para recibir tráfico.
    • /live -> supervivencia del proceso.
    • Validar manualmente los endpoints mediante navegador o curl antes de configurar las sondas.

    Requests y Limits

    Además de la salud, Kubernetes necesita conocer los recursos de hardware (CPU y Memoria) que requieren los contenedores.

    Añadiendo Requests y Limits

    Manifiesto deployment.yaml completo integrando la gestión de recursos:

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-formacion-yaml
  annotations:
    kubernetes.io/change-cause: "Configurados recursos requests y limits"
spec:
  replicas: 1
  selector:
    matchLabels:
      app: demo-formacion-yaml
  template:
    metadata:
      labels:
        app: demo-formacion-yaml
    spec:
      containers:
        - name: demo-formacion
          image: docker.io/ieftraining/demo-formacion:v3
          imagePullPolicy: Always
          ports:
            - containerPort: 8080
          startupProbe:
            httpGet:
              path: /live
              port: 8080
            failureThreshold: 30
            periodSeconds: 1
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /live
              port: 8080
            periodSeconds: 10
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"

    Requests

    Representan los recursos mínimos garantizados que OpenShift reserva en un nodo para poder programar el Pod.

    requests:
  cpu: "100m"      # 100 millicores (0.1 CPU)
  memory: "128Mi"  # 128 Mebibytes

    Limits

    Representan el consumo máximo permitido para el contenedor.

    limits:
  cpu: "500m"      # 500 millicores (0.5 CPU)
  memory: "512Mi"  # 512 Mebibytes

    Aplicación de los cambios

    Opción 1: mediante YAML (Recomendado)

    oc apply -f deployment.yaml

    Opción 2: desde línea de comandos

    oc set resources deployment/demo-formacion-yaml \
  --requests=cpu=100m,memory=128Mi \
  --limits=cpu=500m,memory=512Mi

    Opción 3: desde la consola web

    • Abrir el Deployment demo-formacion-yaml.
    • Seleccionar Actions → Edit Resource Limits (o Edit Deployment).
    • Especificar la CPU y Memoria para Requests y Limits.
    • Guardar los cambios.

    Comprobación de recursos asignados

    Podemos verificar los recursos solicitados ejecutando:

    oc describe pod <nombre-pod>

    Salida típica esperada:

    Containers:
  demo-formacion:
    Requests:
      cpu:      100m
      memory:   128Mi
    Limits:
      cpu:      500m
      memory:   512Mi

    Comprobación del consumo real

    Si el clúster dispone del servidor de métricas (metrics-server):

    oc adm top pods

    Ejemplo de salida:

    NAME                                   CPU(cores)   MEMORY(bytes)
demo-formacion-yaml-6d4b65b98b-x8z2p   3m           45Mi

    Comparación:

    Request CPU       = 100m
Consumo real CPU  = 3m

Request Memoria       = 128Mi
Consumo real Memoria  = 45Mi

    Idea clave

    • Requests: Recursos reservados en el nodo (sirven para planificar dónde colocar el Pod).
    • Limits: Límite máximo infranqueable (si se supera el límite de memoria, la aplicación sufre un error OOMKilled).
    • Consumo real: Uso efectivo detectado en tiempo de ejecución.

    Buenas prácticas para requests y limits

    • Definir siempre límites y reservas de memoria.
    • Ajustar las solicitudes al consumo real observado.
    • Evitar sobredimensionar excesivamente los requests para no desperdiciar capacidad en el clúster.
    • Revisar periódicamente las métricas de utilización.

    Escalado

    Podemos aumentar la capacidad de atención incrementando el número de réplicas en el manifiesto:

    spec:
  replicas: 3

    Aplicando el escalado

    Opción 1: mediante YAML

    Modificar replicas: 3 en deployment.yaml y aplicar:

    oc apply -f deployment.yaml

    Opción 2: desde línea de comandos

    oc scale deployment/demo-formacion-yaml --replicas=3

    Opción 3: desde la consola web

    • Abrir el Deployment demo-formacion-yaml.
    • Ajustar el contador de réplicas en la esquina superior derecha subiendo de 1 a 3.

    Al aplicar los cambios, OpenShift creará 3 Pods idénticos y el Service distribuirá el tráfico entre ellos de forma balanceada.

    Horizontal Pod Autoscaler (HPA)

    También es posible delegar el escalado en un componente automático denominado HPA:

    Más carga de trabajo  -> Más réplicas de Pods
Menos carga de trabajo -> Reducción de Pods

    El HPA utiliza la métrica de consumo real en comparación con los requests definidos en el Deployment para decidir cuándo escalar.

    Nota sobre entornos reales

    Aunque OpenShift facilita la creación de un HPA, el ajuste fino del autoescalado suele requerir pruebas de carga, métricas históricas y un conocimiento detallado del comportamiento de la aplicación.

    Por este motivo, en esta formación introduciremos únicamente el concepto y su funcionamiento general.

    Resumen

    • Una aplicación puede estar viva y no estar preparada.
    • Nuestra aplicación v3 simula esta situación mediante un retraso de 30 segundos en /ready.
    • Readiness decide cuándo un Pod recibe tráfico del Service.
    • Liveness decide cuándo debe reiniciarse un contenedor bloqueado.
    • Startup protege aplicaciones con arranques largos desactivando temporalmente Liveness y Readiness.
    • Requests reservan recursos mínimos para el agendamiento del Pod.
    • Limits establecen consumos máximos permitidos.
    • Requests, limits y consumo real son conceptos distintos.
    • El HPA se apoya en unos requests correctamente definidos para calcular cuándo escalar.
