# Supervisión de aplicaciones en OpenShift

En el apartado anterior hemos desplegado nuestra aplicación mediante un Deployment y la hemos publicado utilizando un Service y una Route.

La aplicación es accesible desde el navegador:

```text
https://demo-formacion.apps...
```

Sin embargo, OpenShift necesita responder continuamente a preguntas como:

- ¿La aplicación sigue funcionando?
- ¿Ha terminado de arrancar?
- ¿Está preparada para recibir tráfico?
- ¿Debo reiniciarla?
- ¿Debo dejar temporalmente de enviarle peticiones?

Para responder a estas preguntas Kubernetes utiliza las denominadas **probes** o **sondas de salud**.

# Simulación de un arranque lento

Para facilitar la explicación de las probes hemos modificado la aplicación.

Cuando el contenedor arranca:

```text
/live  -> OK
/ready -> NOT READY
```

durante aproximadamente 30 segundos.

Pasado ese tiempo:

```text
/live  -> OK
/ready -> READY
```

---

## ¿Por qué hemos hecho esto?

Muchas aplicaciones necesitan un tiempo adicional para completar su inicialización.

Por ejemplo:

- Cargar configuración.
- Inicializar componentes internos.
- Construir cachés.
- Ejecutar migraciones.
- Conectar con servicios externos.
- Cargar información en memoria.

Por tanto:

> Una aplicación puede estar funcionando y, sin embargo, no estar todavía preparada para recibir peticiones.

Esta diferencia es precisamente la que intentan resolver readiness y liveness.

---

# Readiness Probe

La readiness probe responde a una única pregunta:

> ¿Puede este Pod recibir tráfico ahora mismo?

Si la respuesta es afirmativa:

```text
El Service enviará tráfico al Pod.
```

Si la respuesta es negativa:

```text
El Pod continúa ejecutándose,
pero deja de recibir tráfico.
```

# Deployment actual

Partimos de un Deployment similar a éste:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-formacion-yaml
spec:
  replicas: 1

  selector:
    matchLabels:
      app: demo-formacion-yaml

  template:
    metadata:
      labels:
        app: demo-formacion-yaml

    spec:
      containers:
      - name: demo-formacion
        image: docker.io/ieftraining/demo-formacion:v3

        ports:
        - containerPort: 8080
```

Este Deployment funciona correctamente, pero no proporciona a OpenShift ningún mecanismo para determinar cuándo la aplicación está preparada.

---

# Añadiendo una Readiness Probe

Añadimos el siguiente bloque:

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  periodSeconds: 5
```

Deployment completo:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-formacion-yaml
spec:
  replicas: 1

  selector:
    matchLabels:
      app: demo-formacion-yaml

  template:
    metadata:
      labels:
        app: demo-formacion-yaml

    spec:
      containers:
      - name: demo-formacion
        image: docker.io/ieftraining/demo-formacion:v3

        ports:
        - containerPort: 8080

        readinessProbe:
          httpGet:
            path: /ready
            port: 8080
          periodSeconds: 5
```

---

## ¿Qué acabamos de añadir?

Únicamente este bloque:

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
```

A partir de este momento OpenShift realizará peticiones periódicas contra:

```text
/ready
```

para decidir si el Pod puede o no recibir tráfico.
