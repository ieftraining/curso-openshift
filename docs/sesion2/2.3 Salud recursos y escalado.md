## Supervisión de aplicaciones en OpenShift

En el apartado anterior hemos desplegado nuestra aplicación mediante un Deployment y la hemos publicado utilizando un Service y una Route.

La aplicación es accesible desde el navegador:

```text
https://demo-formacion.apps...
```

Sin embargo, OpenShift necesita responder continuamente a preguntas como:

- ¿La aplicación sigue funcionando?
- ¿Ha terminado de arrancar?
- ¿Está preparada para recibir tráfico?
- ¿Debo reiniciarla?
- ¿Debo dejar temporalmente de enviarle peticiones?

Para responder a estas preguntas Kubernetes utiliza las denominadas **probes** o **sondas de salud**.

## Probando los endpoints

```text
https://demo-formacion.apps.../version
```

La propia aplicación nos servirá para entender qué está comprobando OpenShift en cada momento.

## Simulación de un arranque lento

Para facilitar la explicación de las probes hemos modificado la aplicación.

Cuando el contenedor arranca:

```text
/live  -> OK
/ready -> NOT READY
```

durante aproximadamente 30 segundos.

Pasado ese tiempo:

```text
/live  -> OK
/ready -> READY
```

### ¿Por qué hemos hecho esto?

Muchas aplicaciones necesitan un tiempo adicional para completar su inicialización.

Por ejemplo:

- Cargar configuración.
- Inicializar componentes internos.
- Construir cachés.
- Ejecutar migraciones.
- Conectar con servicios externos.
- Cargar información en memoria.

Por tanto:

Una aplicación puede estar funcionando y, sin embargo, no estar todavía preparada para recibir peticiones.

Esta diferencia es precisamente la que intentan resolver readiness y liveness.

## Readiness Probe

La readiness probe responde a una única pregunta:

¿Puede este Pod recibir tráfico ahora mismo?

Si la respuesta es afirmativa:

El Service enviará tráfico al Pod.

Si la respuesta es negativa:

El Pod continúa ejecutándose, pero deja de recibir tráfico.

## Deployment actual

Partimos de un Deployment similar a éste:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-formacion-yaml
spec:
  replicas: 1
  selector:
    matchLabels:
      app: demo-formacion-yaml
  template:
    metadata:
      labels:
        app: demo-formacion-yaml
    spec:
      containers:
        - name: demo-formacion
          image: docker.io/ieftraining/demo-formacion:v3
          ports:
            - containerPort: 8080
```

Este Deployment funciona correctamente, pero no proporciona a OpenShift ningún mecanismo para determinar cuándo la aplicación está preparada.

## Añadiendo una Readiness Probe

Añadimos el siguiente bloque:

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  periodSeconds: 5
```

Deployment completo:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-formacion-yaml
spec:
  replicas: 1
  selector:
    matchLabels:
      app: demo-formacion-yaml
  template:
    metadata:
      labels:
        app: demo-formacion-yaml
    spec:
      containers:
        - name: demo-formacion
          image: docker.io/ieftraining/demo-formacion:v3
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            periodSeconds: 5
```

### ¿Qué acabamos de añadir?

Únicamente este bloque:

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
```

A partir de este momento OpenShift realizará peticiones periódicas contra:

```text
/ready
```

para decidir si el Pod puede o no recibir tráfico.

## Observando el comportamiento

Podemos monitorizar el estado mediante:

```bash
oc get pods -w
```

Al arrancar una nueva revisión veremos algo parecido a:

```text
0/1 Running
```

Esto significa:

El contenedor está ejecutándose, pero la aplicación todavía no está preparada.

Recordemos:

```text
/live  -> OK
/ready -> NOT READY
```

durante los primeros 30 segundos.

Pasados esos 30 segundos:

```text
/ready -> READY
```

y observaremos:

```text
1/1 Running
```

porque OpenShift considera que la aplicación puede empezar a recibir tráfico.

## Idea clave

Durante esos 30 segundos:

La aplicación ya estaba funcionando.

Lo único que ocurría es que:

OpenShift todavía no la consideraba preparada.

Ésa es exactamente la misión de la readiness probe.

## ¿Qué debe comprobar una Readiness Probe?

Todo aquello que determine si la aplicación puede atender peticiones correctamente.

Por ejemplo:

- Configuración cargada.
- Dependencias inicializadas.
- Cachés preparadas.
- Base de datos accesible.
- Servicios críticos disponibles.

La idea es:

La aplicación sigue viva, pero todavía no está lista para prestar servicio.

## Liveness Probe

La liveness probe responde a otra pregunta:

¿La aplicación sigue funcionando correctamente?

## Añadiendo una Liveness Probe

Añadimos:

```yaml
livenessProbe:
  httpGet:
    path: /live
    port: 8080
  periodSeconds: 10
```

Deployment completo:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-formacion-yaml
spec:
  replicas: 1
  selector:
    matchLabels:
      app: demo-formacion-yaml
  template:
    metadata:
      labels:
        app: demo-formacion-yaml
    spec:
      containers:
        - name: demo-formacion
          image: docker.io/ieftraining/demo-formacion:v3
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /live
              port: 8080
            periodSeconds: 10
```

### ¿Qué se ha añadido?

```yaml
livenessProbe:
  httpGet:
    path: /live
    port: 8080
```

### ¿Qué hace?

OpenShift ejecuta periódicamente:

```text
GET /live
```

Si recibe:

```text
OK
```

no realiza ninguna acción.

Si la comprobación falla repetidamente:

```text
ERROR
```

o

```text
timeout
```

reiniciará automáticamente el contenedor.

## ¿Qué debe comprobar una Liveness Probe?

Únicamente aquello que permita saber que la aplicación sigue viva.

Por ejemplo:

- El proceso principal sigue ejecutándose.
- El servidor HTTP responde.
- La aplicación no está bloqueada.

## Readiness y Liveness no son intercambiables

### Readiness

Pregunta:

```text
¿Puedo recibir tráfico?
```

Consecuencia:

```text
Entrar o salir del Service.
```

### Liveness

Pregunta:

```text
¿Sigo funcionando?
```

Consecuencia:

```text
Reinicio del contenedor.
```

### Ejemplo práctico

Supongamos que una base de datos deja de responder temporalmente.

Podríamos tener:

```text
/live  -> OK
/ready -> ERROR
```

Resultado:

```text
El Pod deja de recibir tráfico.
El contenedor no se reinicia.
```

Cuando la base de datos vuelva a estar disponible:

```text
/ready -> READY
```

todo volverá a la normalidad automáticamente.

Si la comprobación de la base de datos se hubiera incluido en:

```text
/live
```

obtendríamos:

```text
Reinicio
↓
Reinicio
↓
Reinicio
```

sin resolver realmente el problema.

## Startup Probe

Algunas aplicaciones necesitan mucho tiempo para arrancar.

Ejemplos habituales:

- Aplicaciones Java empresariales.
- Middleware comercial.
- Sistemas que ejecutan migraciones al inicio.

Para estos escenarios existe startupProbe.

## Añadiendo Startup Probe

Añadimos:

```yaml
startupProbe:
  httpGet:
    path: /live
    port: 8080
  failureThreshold: 30
  periodSeconds: 1
```

Deployment completo:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-formacion-yaml
spec:
  replicas: 1
  selector:
    matchLabels:
      app: demo-formacion-yaml
  template:
    metadata:
      labels:
        app: demo-formacion-yaml
    spec:
      containers:
        - name: demo-formacion
          image: docker.io/ieftraining/demo-formacion:v3
          ports:
            - containerPort: 8080
          startupProbe:
            httpGet:
              path: /live
              port: 8080
            failureThreshold: 30
            periodSeconds: 1
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /live
              port: 8080
            periodSeconds: 10
```

### ¿Qué acabamos de añadir?

```yaml
startupProbe:
  httpGet:
    path: /live
    port: 8080
```

Esta sonda proporciona tiempo adicional a aplicaciones con arranques lentos.

Mientras startupProbe no finalice correctamente:

- Readiness permanece inactiva.
- Liveness permanece inactiva.

La aplicación puede completar tranquilamente su inicialización.

## Buenas prácticas para las probes

Utilizar endpoints específicos:

```text
/live
/ready
```

Evitar:

```text
/
```

Mantener las comprobaciones simples y rápidas.

Separar claramente responsabilidades:

```text
/ready -> disponibilidad para recibir tráfico
/live  -> supervivencia de la aplicación
```

Validar manualmente:

```text
/ready
/live
/version
```

antes de configurar las sondas.

## Requests y Limits

Además de la salud de las aplicaciones, Kubernetes necesita conocer los recursos que requieren.

## Añadiendo Requests y Limits

Añadimos:

```yaml
resources:
  requests:
    cpu: "100m"
    memory: "128Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"
```

Deployment completo:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-formacion-yaml
spec:
  replicas: 1
  selector:
    matchLabels:
      app: demo-formacion-yaml
  template:
    metadata:
      labels:
        app: demo-formacion-yaml
    spec:
      containers:
        - name: demo-formacion
          image: docker.io/ieftraining/demo-formacion:v3
          ports:
            - containerPort: 8080
          startupProbe:
            httpGet:
              path: /live
              port: 8080
            failureThreshold: 30
            periodSeconds: 1
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /live
              port: 8080
            periodSeconds: 10
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"
```

### Requests

Representan los recursos mínimos que la aplicación necesita.

```yaml
requests:
  cpu: "100m"
  memory: "128Mi"
```

### Limits

Representan el consumo máximo permitido.

```yaml
limits:
  cpu: "500m"
  memory: "512Mi"
```

## Comprobación de recursos asignados

Podemos verificar los valores configurados mediante:

```bash
oc describe pod <nombre-pod>
```

Salida típica:

```text
Requests:
  cpu:      100m
  memory:   128Mi

Limits:
  cpu:      500m
  memory:   512Mi
```

## Comprobación del consumo real

Si el clúster dispone de métricas:

```bash
oc adm top pods
```

Ejemplo:

```text
NAME                   CPU   MEMORY
demo-formacion-yaml    3m    45Mi
```

Comparación:

```text
Request CPU       = 100m
Consumo real CPU  = 3m

Request Memoria       = 128Mi
Consumo real Memoria  = 45Mi
```

### Idea clave

```text
Requests = recursos reservados
Limits   = consumo máximo permitido
Consumo  = utilización real observada
```

OpenShift utiliza los requests para planificar dónde ejecutar los Pods y los limits para evitar consumos excesivos.

## Buenas prácticas para requests y limits

- Definir siempre memoria.
- Ajustar valores al consumo real.
- Evitar sobredimensionar requests.
- Revisar periódicamente las métricas de utilización.

## Escalado

Podemos aumentar capacidad incrementando el número de réplicas:

```yaml
replicas: 3
```

El Service distribuirá automáticamente el tráfico entre los Pods.

## Horizontal Pod Autoscaler (HPA)

También es posible realizar escalado automático:

```text
Más carga -> más Pods
Menos carga -> menos Pods
```

El HPA utiliza los requests como referencia para calcular la utilización de recursos.

### Nota sobre entornos reales

Aunque OpenShift facilita la creación de un HPA, el ajuste fino del autoescalado suele requerir pruebas de carga, métricas históricas y conocimiento detallado de la aplicación.

Por este motivo, en esta formación introduciremos únicamente el concepto y su funcionamiento general.

## Ideas clave

- Una aplicación puede estar viva y no estar preparada.
- Nuestra aplicación v3 simula esta situación mediante un retraso de 30 segundos en /ready.
- Readiness decide cuándo un Pod recibe tráfico.
- Liveness decide cuándo debe reiniciarse un contenedor.
- Startup protege aplicaciones con arranques largos.
- Requests reservan recursos mínimos.
- Limits establecen consumos máximos.
- Requests, limits y consumo real son conceptos distintos.
- El HPA se apoya en unos requests correctamente definidos.
- El ajuste avanzado del autoescalado suele realizarse en escenarios productivos reales.
