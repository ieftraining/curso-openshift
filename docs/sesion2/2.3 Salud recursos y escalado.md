## 2.3 Salud, recursos y escalado

### Objetivos de aprendizaje

Al finalizar este apartado serás capaz de:

- Comprender por qué un Pod en estado `Running` no siempre está preparado para prestar servicio.
- Diferenciar `startupProbe`, `readinessProbe` y `livenessProbe`.
- Configurar comprobaciones de salud mediante sondas HTTP.
- Comprender cómo influyen las sondas en el tráfico y en el reinicio de los contenedores.
- Definir `requests` y `limits` básicos de CPU y memoria.
- Comprobar los recursos configurados y compararlos con el consumo real.
- Escalar manualmente una aplicación aumentando o reduciendo su número de réplicas.

### De una aplicación desplegada a una aplicación operable

En los apartados anteriores hemos aprendido a desplegar una aplicación, actualizarla mediante un `Deployment` y publicarla utilizando un `Service` y una `Route`.

Sin embargo, que un contenedor esté ejecutándose no significa necesariamente que la aplicación esté preparada para atender peticiones correctamente.

OpenShift debe poder responder a tres preguntas diferentes:

| Situación | Pregunta que debe responder OpenShift | Acción esperada |
|---|---|---|
| La aplicación todavía está arrancando | ¿Ha terminado de iniciarse? | Esperar antes de aplicar el resto de comprobaciones |
| La aplicación funciona, pero temporalmente no puede atender peticiones | ¿Está preparada para recibir tráfico? | Dejar de enviarle tráfico hasta que se recupere |
| La aplicación se ha bloqueado y no se recuperará por sí sola | ¿Sigue funcionando? | Reiniciar el contenedor |

Kubernetes responde a estas preguntas mediante las **probes** o **sondas de salud**:

- `startupProbe`: comprueba si la aplicación ha terminado de arrancar.
- `readinessProbe`: determina si el Pod puede recibir tráfico.
- `livenessProbe`: determina si el contenedor sigue funcionando o debe reiniciarse.

!!! tip "Idea clave"
    `Running` indica que el contenedor está en ejecución. No garantiza que la aplicación haya terminado de arrancar ni que pueda atender peticiones correctamente.

### Actualización a la versión v3

Hasta este momento estamos trabajando con la versión v2 de la aplicación, utilizada para demostrar actualizaciones de imagen, *rollouts* y *rollbacks*.

Para estudiar las sondas de salud desplegaremos una nueva versión. La versión v3 incorpora tres endpoints específicos:

- `/version`: muestra la versión de la aplicación.
- `/live`: indica si el proceso de la aplicación sigue funcionando.
- `/ready`: indica si la aplicación está preparada para recibir tráfico.

#### Registrando la causa del cambio y actualizando la imagen

Para que la causa del cambio quede registrada en el historial de revisiones del `Deployment`, actualizaremos la imagen e incluiremos la anotación `kubernetes.io/change-cause`.

##### Opción 1: mediante YAML (recomendado)

Actualizamos el archivo `deployment.yaml`:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-formacion-yaml
  annotations:
    kubernetes.io/change-cause: "Actualizacion a v3. Incorpora endpoints /version, /live y /ready para demostracion de probes."
spec:
  replicas: 1
  selector:
    matchLabels:
      app: demo-formacion-yaml
  template:
    metadata:
      labels:
        app: demo-formacion-yaml
    spec:
      containers:
        - name: demo-formacion
          image: docker.io/ieftraining/demo-formacion:v3
          imagePullPolicy: Always
          ports:
            - containerPort: 8080
```

Aplicamos los cambios:

```bash
oc apply -f deployment.yaml
```

##### Opción 2: desde la línea de comandos

```bash
oc set image deployment/demo-formacion-yaml \
  demo-formacion=docker.io/ieftraining/demo-formacion:v3

oc annotate deployment/demo-formacion-yaml \
  kubernetes.io/change-cause="Actualizacion a v3. Incorpora endpoints /version, /live y /ready para demostracion de probes." \
  --overwrite
```

##### Opción 3: desde la consola web

1. Abrir el `Deployment`.
2. Seleccionar **Actions → Edit Deployment**.
3. Modificar la imagen del contenedor a `docker.io/ieftraining/demo-formacion:v3`.
4. Actualizar la anotación `kubernetes.io/change-cause` dentro de `metadata.annotations`.
5. Guardar los cambios.

OpenShift iniciará automáticamente un nuevo *rollout*.

#### Comprobando el despliegue

```bash
oc rollout status deployment/demo-formacion-yaml
```

También podemos observar la creación del nuevo Pod:

```bash
oc get pods -w
```

#### Consultando el historial

```bash
oc rollout history deployment/demo-formacion-yaml
```

Ejemplo de resultado esperado:

```text
REVISION  CHANGE-CAUSE
1         Creacion inicial de la aplicacion v1.
2         Actualizacion a v2. Nueva version de la aplicacion para demostracion de actualizaciones y rollback.
3         Actualizacion a v3. Incorpora endpoints /version, /live y /ready para demostracion de probes.
```

Podemos consultar el detalle de una revisión concreta:

```bash
oc rollout history deployment/demo-formacion-yaml --revision=3
```

#### Verificando la nueva versión

Consultamos el endpoint `/version` utilizando la URL de nuestra `Route`:

```text
https://<URL_DE_LA_ROUTE>/version
```

Resultado esperado:

```json
{
  "version": "v3"
}
```

A partir de este momento utilizaremos `/live` y `/ready` para comprender cómo OpenShift supervisa la aplicación.

### Simulación de un arranque lento

Para facilitar la demostración, la versión v3 simula que necesita aproximadamente 30 segundos para completar su inicialización.

Durante ese periodo:

```text
/live  → OK (200)
/ready → NOT READY (500)
```

Una vez finalizada la inicialización:

```text
/live  → OK (200)
/ready → READY (200)
```

Muchas aplicaciones necesitan un tiempo adicional para:

- cargar su configuración;
- inicializar componentes internos;
- construir cachés;
- ejecutar migraciones;
- conectarse con servicios externos;
- cargar información en memoria.

Por tanto, **una aplicación puede estar funcionando y, sin embargo, no estar todavía preparada para recibir peticiones**.

### Readiness Probe

La `readinessProbe` responde a esta pregunta:

> **¿Puede este Pod recibir tráfico ahora mismo?**

- Si la comprobación es correcta, el Pod puede formar parte de los endpoints disponibles del `Service`.
- Si la comprobación falla, el Pod continúa ejecutándose, pero deja temporalmente de recibir tráfico a través del `Service`.
- Si vuelve a estar preparado, OpenShift lo incorpora de nuevo automáticamente.

#### Añadiendo una Readiness Probe

Añadimos el siguiente bloque dentro de la definición del contenedor:

```yaml
readinessProbe:
  httpGet:
    path: /ready
    port: 8080
  periodSeconds: 5
```

OpenShift realizará una petición HTTP periódica al endpoint `/ready`. En este ejemplo, la comprobación se repite cada cinco segundos.

Aplicamos el manifiesto actualizado:

```bash
oc apply -f deployment.yaml
```

También podríamos configurarla desde la línea de comandos:

```bash
oc set probe deployment/demo-formacion-yaml \
  --readiness \
  --get-url=http://:8080/ready \
  --period-seconds=5
```

Desde la consola web podemos abrir el `Deployment`, seleccionar **Actions → Edit Deployment**, incorporar el bloque `readinessProbe` dentro del contenedor y guardar los cambios.

#### Observando el comportamiento

Monitorizamos el estado del Pod:

```bash
oc get pods -w
```

Durante el arranque veremos algo parecido a:

```text
NAME                                    READY   STATUS    RESTARTS   AGE
demo-formacion-yaml-6d4b65b98b-x8z2p   0/1     Running   0          5s
```

El contenedor está en estado `Running`, pero la columna `READY` muestra `0/1`: la aplicación todavía no está preparada para recibir tráfico.

Pasados aproximadamente 30 segundos, `/ready` devuelve una respuesta correcta:

```text
NAME                                    READY   STATUS    RESTARTS   AGE
demo-formacion-yaml-6d4b65b98b-x8z2p   1/1     Running   0          35s
```

`1/1` indica que OpenShift ya considera preparado el contenedor y que el Pod puede recibir tráfico a través del `Service`.

!!! tip "Idea clave"
    Durante los primeros segundos la aplicación estaba ejecutándose, pero todavía no estaba preparada. Esa es la diferencia entre el estado `Running` y la condición `Ready`.

#### ¿Qué debe comprobar una Readiness Probe?

Debe comprobar aquello que determine si la aplicación puede atender peticiones correctamente, por ejemplo:

- que se haya cargado la configuración necesaria;
- que hayan finalizado las tareas de inicialización;
- que las cachés necesarias estén preparadas;
- que estén disponibles las dependencias imprescindibles para responder.

La comprobación debe ser rápida y centrarse únicamente en la capacidad actual de prestar servicio.

### Liveness Probe

La `livenessProbe` responde a una pregunta diferente:

> **¿La aplicación sigue funcionando o se ha quedado bloqueada?**

Si la comprobación falla repetidamente, Kubernetes reinicia el contenedor de acuerdo con la política de reinicio del Pod.

#### Añadiendo una Liveness Probe

Añadimos la comprobación sobre el endpoint `/live`:

```yaml
livenessProbe:
  httpGet:
    path: /live
    port: 8080
  periodSeconds: 10
```

En este ejemplo, OpenShift realiza una petición HTTP a `/live` cada diez segundos:

- Si obtiene una respuesta correcta, no realiza ninguna acción.
- Si la comprobación falla el número de veces configurado, reinicia el contenedor.

Aplicamos el manifiesto actualizado:

```bash
oc apply -f deployment.yaml
```

También podríamos configurarla desde la línea de comandos:

```bash
oc set probe deployment/demo-formacion-yaml \
  --liveness \
  --get-url=http://:8080/live \
  --period-seconds=10
```

Desde la consola web podemos abrir el `Deployment`, seleccionar **Actions → Edit Deployment**, añadir el bloque `livenessProbe` y guardar los cambios.

#### ¿Qué debe comprobar una Liveness Probe?

Debe comprobar únicamente aquello que permita determinar si el proceso se ha bloqueado y necesita reiniciarse, por ejemplo:

- que el proceso principal siga respondiendo;
- que el servidor web o la API responda a una comprobación básica;
- que no exista un bloqueo interno del que la aplicación no pueda recuperarse.

### Readiness y Liveness no son intercambiables

| Sonda | Pregunta | Consecuencia de un fallo |
|---|---|---|
| `readinessProbe` | ¿Puede recibir tráfico? | El Pod deja temporalmente de recibir tráfico del `Service` |
| `livenessProbe` | ¿Sigue funcionando? | Kubernetes reinicia el contenedor |

#### Ejemplo práctico

Supongamos que una base de datos externa deja de responder temporalmente:

```text
/live  → OK
/ready → ERROR
```

El proceso de la aplicación continúa funcionando, pero no puede prestar el servicio correctamente mientras la base de datos no esté disponible.

- La `readinessProbe` debe fallar para que el Pod deje de recibir tráfico temporalmente.
- La `livenessProbe` puede continuar respondiendo correctamente porque reiniciar el contenedor no solucionaría la caída de una dependencia externa.
- Cuando la base de datos se recupere, `/ready` volverá a responder correctamente y el Pod recibirá tráfico de nuevo.

!!! warning "Evitar reinicios inútiles"
    No debemos incluir indiscriminadamente todas las dependencias externas en la `livenessProbe`. Si el reinicio del contenedor no puede resolver el fallo, podríamos provocar reinicios continuos sin corregir la causa real.

### Startup Probe

Algunas aplicaciones, como determinadas aplicaciones Java, WildFly o Spring Boot, pueden necesitar bastante tiempo para arrancar.

La `startupProbe` protege este periodo inicial. Mientras no haya tenido éxito, Kubernetes no ejecuta las comprobaciones de `livenessProbe` y `readinessProbe`.

Esto evita que una aplicación lenta sea reiniciada antes de haber terminado de inicializarse.

#### Añadiendo una Startup Probe

```yaml
startupProbe:
  httpGet:
    path: /live
    port: 8080
  failureThreshold: 30
  periodSeconds: 1
```

Con esta configuración, la aplicación dispone de aproximadamente 30 segundos para superar la comprobación de arranque:

```text
failureThreshold × periodSeconds = 30 × 1 segundo
```

Cuando `startupProbe` tiene éxito, deja de ejecutarse y comienzan las comprobaciones habituales de readiness y liveness.

Aplicamos el manifiesto actualizado:

```bash
oc apply -f deployment.yaml
```

También podríamos configurarla desde la línea de comandos:

```bash
oc set probe deployment/demo-formacion-yaml \
  --startup \
  --get-url=http://:8080/live \
  --failure-threshold=30 \
  --period-seconds=1
```

Desde la consola web podemos abrir el `Deployment`, seleccionar **Actions → Edit Deployment**, añadir el bloque `startupProbe` y guardar los cambios.

#### Resumen de las tres sondas

| Sonda | Pregunta principal | Acción asociada |
|---|---|---|
| `startupProbe` | ¿Ha terminado de arrancar? | Protege el periodo de inicio antes de activar el resto de las sondas |
| `readinessProbe` | ¿Puede recibir tráfico? | Incluye o retira el Pod de los endpoints disponibles del `Service` |
| `livenessProbe` | ¿Sigue funcionando? | Reinicia el contenedor cuando la aplicación no se recupera por sí sola |

### Buenas prácticas para las sondas

- Utilizar endpoints dedicados, como `/live` y `/ready`.
- Mantener las comprobaciones simples y rápidas.
- Evitar operaciones pesadas o pruebas innecesariamente complejas.
- No utilizar liveness para fallos que un reinicio no puede solucionar.
- Ajustar los tiempos y umbrales al comportamiento real de la aplicación.
- Probar manualmente los endpoints antes de configurar las sondas.

### ¿Cuántos recursos necesita la aplicación?

Las sondas permiten que OpenShift conozca el estado de la aplicación. Sin embargo, para ejecutar el Pod también necesita saber cuánta CPU y memoria requiere.

Esta información se declara mediante `requests` y `limits`:

- Los **requests** expresan los recursos que Kubernetes debe tener en cuenta para decidir en qué nodo puede programar el Pod.
- Los **limits** establecen el consumo máximo permitido para el contenedor.

#### Unidades de CPU y memoria

En Kubernetes es habitual expresar la CPU en *millicores*:

- `100m` equivale a 0,1 CPU.
- `500m` equivale a 0,5 CPU.
- `1000m` equivale a 1 CPU.

La memoria suele expresarse mediante unidades binarias como `Mi` y `Gi`:

- `128Mi` representa 128 mebibytes.
- `1Gi` representa 1 gibibyte.

### Añadiendo Requests y Limits

Añadimos el siguiente bloque dentro de la definición del contenedor:

```yaml
resources:
  requests:
    cpu: "100m"
    memory: "128Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"
```

Esta configuración puede leerse así:

> Para programar el Pod, Kubernetes tendrá en cuenta que el contenedor solicita 100 millicores de CPU y 128 MiB de memoria. Una vez en ejecución, permitimos que consuma hasta 500 millicores de CPU y 512 MiB de memoria.

#### Requests

```yaml
requests:
  cpu: "100m"
  memory: "128Mi"
```

El planificador de Kubernetes utiliza estos valores para seleccionar un nodo con capacidad suficiente para alojar el Pod.

Los `requests` no representan necesariamente el consumo real y permanente del contenedor. Son la referencia que utiliza Kubernetes para planificar su ubicación y gestionar la capacidad declarada del clúster.

#### Limits

```yaml
limits:
  cpu: "500m"
  memory: "512Mi"
```

Los límites controlan cuánto puede consumir el contenedor, pero CPU y memoria se comportan de manera diferente:

- Si el contenedor intenta utilizar más CPU de la permitida, su consumo se restringe (*CPU throttling*).
- Si intenta superar el límite de memoria y no puede liberar suficiente memoria, puede finalizar con un error `OOMKilled` y ser reiniciado.

!!! note
    Los valores utilizados son adecuados para la práctica del curso. En un entorno real deberían ajustarse a partir de pruebas y métricas de consumo representativas.

### Deployment consolidado

El manifiesto completo integra la versión v3, las tres sondas y la configuración de recursos:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo-formacion-yaml
  annotations:
    kubernetes.io/change-cause: "Configuradas probes y recursos para la aplicacion v3"
spec:
  replicas: 1
  selector:
    matchLabels:
      app: demo-formacion-yaml
  template:
    metadata:
      labels:
        app: demo-formacion-yaml
    spec:
      containers:
        - name: demo-formacion
          image: docker.io/ieftraining/demo-formacion:v3
          imagePullPolicy: Always
          ports:
            - containerPort: 8080
          startupProbe:
            httpGet:
              path: /live
              port: 8080
            failureThreshold: 30
            periodSeconds: 1
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /live
              port: 8080
            periodSeconds: 10
          resources:
            requests:
              cpu: "100m"
              memory: "128Mi"
            limits:
              cpu: "500m"
              memory: "512Mi"
```

Aplicamos el manifiesto:

```bash
oc apply -f deployment.yaml
```

También podemos configurar los recursos desde la línea de comandos:

```bash
oc set resources deployment/demo-formacion-yaml \
  --requests=cpu=100m,memory=128Mi \
  --limits=cpu=500m,memory=512Mi
```

Desde la consola web podemos abrir el `Deployment` y utilizar **Actions → Edit Resource Limits** o **Actions → Edit Deployment**, según la versión y la perspectiva de la consola.

### Comprobación del consumo real

Si la recopilación de métricas está disponible en el clúster, podemos consultar el consumo actual:

```bash
oc adm top pods
```

Ejemplo de salida:

```text
NAME                                    CPU(cores)   MEMORY(bytes)
demo-formacion-yaml-6d4b65b98b-x8z2p   3m           45Mi
```

En este ejemplo podemos distinguir tres valores diferentes:

```text
Request de CPU      = 100m
Consumo real de CPU = 3m
Límite de CPU       = 500m

Request de memoria      = 128Mi
Consumo real de memoria = 45Mi
Límite de memoria       = 512Mi
```

!!! tip "Idea clave"
    Los `requests` sirven de referencia para programar el Pod, los `limits` restringen el consumo máximo y las métricas muestran el uso real en un momento determinado.

### Buenas prácticas para Requests y Limits

- Definir valores coherentes con el comportamiento real de la aplicación.
- Evitar requests excesivamente altos que dificulten la programación de los Pods.
- Evitar límites de memoria demasiado bajos que provoquen errores `OOMKilled`.
- Revisar las métricas durante periodos representativos antes de ajustar los valores.
- Comprobar el efecto de los cambios en entornos controlados antes de aplicarlos en producción.

La clasificación de calidad de servicio de los Pods y las políticas de recursos a nivel de proyecto se estudiarán posteriormente, en el apartado dedicado a la gestión avanzada de recursos y cuotas.

### Escalado manual

Hasta ahora hemos ejecutado una única réplica de la aplicación. Si necesitamos aumentar su capacidad, podemos incrementar manualmente el número de réplicas del `Deployment`:

```bash
oc scale deployment/demo-formacion-yaml --replicas=3
```

Comprobamos el resultado:

```bash
oc get deployment demo-formacion-yaml
oc get pods
```

Ejemplo:

```text
NAME                  READY   UP-TO-DATE   AVAILABLE   AGE
demo-formacion-yaml   3/3     3            3           25m
```

El `Deployment` mantiene ahora tres Pods con la misma configuración. El `Service` puede distribuir el tráfico entre los Pods que estén preparados.

También podemos reducir de nuevo el número de réplicas:

```bash
oc scale deployment/demo-formacion-yaml --replicas=1
```

!!! note
    El escalado manual permite decidir directamente el número de réplicas, pero requiere intervención. En el apartado 3.2 estudiaremos desde cero cómo utilizar el Horizontal Pod Autoscaler para adaptar automáticamente el número de Pods a la carga observada.

### Ideas clave para recordar

!!! tip "Resumen"
    - Un contenedor en estado `Running` no tiene por qué estar preparado para recibir tráfico.
    - `startupProbe` protege el periodo inicial de arranque.
    - `readinessProbe` decide si el Pod puede recibir tráfico del `Service`.
    - `livenessProbe` permite reiniciar un contenedor que se ha bloqueado.
    - Readiness y liveness no son intercambiables porque provocan acciones diferentes.
    - Los `requests` orientan al planificador sobre los recursos necesarios para ubicar el Pod.
    - Los `limits` restringen el consumo máximo de CPU y memoria.
    - Superar un límite de CPU puede provocar restricción de uso; superar el límite de memoria puede provocar `OOMKilled`.
    - El escalado manual modifica directamente el número de réplicas de un `Deployment`.
    - El autoescalado mediante HPA se desarrollará en el apartado 3.2.
